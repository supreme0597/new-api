## 1. 系统部署与初始化

### 1.1 首次访问

部署完成后，浏览器访问系统首页，会自动跳转到初始化页面 `/api/setup`。

首次设置需要配置：

| 配置项 | 说明 |
|--------|------|
| 管理员用户名 | 超级管理员账号 |
| 管理员密码 | 登录密码 |
| 管理员邮箱 | 用于接收通知 |

> **注意**：初始化完成后，`/api/setup` 接口将自动关闭，防止被重复利用。

### 1.2 系统概览

登录后进入**仪表盘**，可以看到：

- **总请求数** — 系统累计处理的 API 请求总数
- **总消耗额度** — 所有用户累计消耗的配额
- **活跃用户数** — 近期有请求记录的用户数
- **渠道状态** — 各渠道的连接状态和响应时间

## 3. 认证与安全配置

路径：**系统设置 → 认证安全**

### 3.1 OAuth 登录配置

支持以下第三方登录：

| 提供商 | 配置字段 |
|--------|---------|
| GitHub | Client ID, Client Secret |
| Discord | Client ID, Client Secret |
| 通用 OIDC | Issuer URL, Client ID, Client Secret, Scopes |
| Linux DO | Client ID, Client Secret |
| 微信 | App ID, App Secret |
| Telegram | Bot Token |
| 自定义 OAuth | 自定义配置（支持任意 OAuth2 提供商） |

**配置步骤**：

1. 在第三方平台创建 OAuth App，设置回调地址为 `https://您的域名/api/oauth/{provider}`
2. 在**系统设置 → 认证安全 → OAuth 登录**中填入对应参数
3. 开启对应的登录方式开关

### 3.2 LDAP 登录

支持通过 LDAP / Active Directory 进行企业员工认证。

**配置参数**：

| 字段 | 说明 | 示例 |
|------|------|------|
| 启用 LDAP | 开关 | `true` |
| 服务器地址 | LDAP 服务器地址含端口 | `ldap.example.com:389` |
| 管理员 DN | 绑定管理员账号 | `cn=admin,dc=example,dc=com` |
| 管理员密码 | 绑定密码 | |
| 搜索过滤器 | 用户搜索模板 | `(employeeID=%s)` 或 `(sAMAccountName=%s)` |
| 搜索基准 DN | Base DN | `dc=example,dc=com` |
| 使用 LDAPS | 是否启用 TLS 加密 | |
| 跳过 TLS 验证 | 开发环境使用 | |
| 属性映射 | LDAP 属性到系统字段映射 | `{"real_name":"cn","email":"mail","department":"department"}` |
| 允许群组 | 允许访问的 LDAP 群组列表，逗号分隔 | `AI-Users,Developers` |
| 群组属性 | LDAP 群组属性名 | `memberOf` |

**LDAP 认证流程**：
1. 用户在登录页选择"LDAP 登录"，输入工号和密码
2. 系统连接 LDAP 服务器验证密码
3. 验证通过后自动创建用户（用户名=工号，分组=default）
4. 用户可以使用工号作为 API Key 调用接口（需同时提供 LDAP-Password 请求头）

**LDAP 工号令牌认证**（适用于机器调用场景）：

```
Authorization: Bearer <工号>
LDAP-Password: <LDAP密码>
```

> 系统会自动创建令牌（Key=工号，名称为"LDAP 工号令牌"，无限额度，永不过期），后续相同工号请求直接复用令牌，避免重复 LDAP 查询。

### 3.3 登录安全

| 配置项 | 说明 |
|--------|------|
| 密码登录 | 是否允许密码登录 |
| 注册审核 | 新注册用户是否需要管理员审核 |
| 邮箱验证 | 注册是否需要邮箱验证 |
| Turnstile / reCAPTCHA | 验证码配置 |
| 登录频率限制 | 登录接口的请求频率上限 |

### 3.4 WebAuthn / Passkeys

支持无密码登录，使用设备生物识别（指纹、面部等）。

管理路径：**系统设置 → 认证安全 → Passkey 设置**

### 3.5 双因素认证（2FA）

支持为管理员账户开启 TOTP 双因素认证，增强后台安全。

管理员也可以在**用户管理**中查看和重置普通用户的 2FA。

### 3.6 IP 访问控制

路径：**系统设置 → 安全**

| 配置项 | 说明 |
|--------|------|
| IP 白名单 | 仅允许列表中的 IP 访问管理后台 |
| IP 黑名单 | 禁止列表中的 IP 访问系统 |

## 4. 渠道管理

渠道是上游 AI 提供商的连接配置。系统支持 40+ 种渠道类型。

路径：**渠道管理**

### 4.1 添加渠道

点击"添加渠道"，选择渠道类型，填写以下核心参数：

| 参数 | 说明 |
|------|------|
| 名称 | 渠道名称，便于管理 |
| 渠道类型 | 选择上游提供商（OpenAI、Claude、Gemini、Azure 等） |
| API Key | 上游提供商的 API 密钥 |
| 代理地址 | 可选，如果通过代理访问上游 |
| 模型 | 该渠道支持的模型列表，用逗号分隔 |
| 分组 | 渠道所属分组，只有该分组的用户/令牌可使用 |
| 权重 | 负载均衡权重，权重越高流量分配越多 |
| 优先级 | 优先级越高越优先被选中 |
| 模型映射 | 将请求的模型名映射为上游实际模型名 |
| 状态码映射 | 将上游返回的状态码映射为自定义状态码 |
| 自动禁用 | 连续失败达到阈值后自动禁用渠道 |
| 测试模型 | 用于连通性测试的模型名 |
| 标签 | 渠道标签，用于批量管理 |
| 所属人 | 渠道所有者（支持渠道归属到指定用户） |

### 4.2 渠道类型

支持的渠道类型包括但不限于：

| 类型 | 说明 |
|------|------|
| OpenAI | OpenAI API |
| Claude | Anthropic Claude API |
| Gemini | Google Gemini API |
| Azure | Azure OpenAI Service |
| AWS Bedrock | AWS Bedrock 服务 |
| 通义千问 | 阿里云通义千问 |
| 文心一言 | 百度文心一言 |
| DeepSeek | DeepSeek API |
| Moonshot | Moonshot API |
| Groq | Groq API |
| ... | 共 40+ 种 |

### 4.3 渠道测试

- **单个测试**：点击渠道的"测试"按钮，使用配置的测试模型发起请求
- **批量测试**：在渠道列表页点击"全部测试"，系统逐一验证所有渠道
- **余额查询**：部分渠道支持自动查询余额

### 4.4 渠道批量操作

| 操作 | 说明 |
|------|------|
| 批量禁用 | 按标签批量禁用渠道 |
| 批量启用 | 按标签批量启用渠道 |
| 批量设置标签 | 为多个渠道统一设置标签 |
| 批量删除 | 删除多个渠道 |
| 批量多 Key 管理 | 管理渠道的多 API Key 轮询 |

### 4.5 上游模型检测

系统可以自动检测渠道上游可用的模型列表：

- **检测单个渠道**：在渠道详情页点击"获取模型列表"
- **检测全部渠道**：在渠道列表页点击"检测全部上游模型更新"
- **应用更新**：将检测到的模型变动应用到渠道配置

### 4.6 渠道归属（Channel Ownership）

渠道可以归属于指定用户，该用户可以在"我的渠道"页面管理自己的渠道。适用于渠道分销场景。

### 4.7 Ollama 模型管理

支持通过 Ollama 拉取和管理本地模型：

- 拉取模型：`POST /api/channel/ollama/pull`
- 删除模型：`DELETE /api/channel/ollama/delete`
- 查看版本：`GET /api/channel/ollama/version/:id`

### 4.8 Codex OAuth

部分渠道支持通过 OAuth 授权方式接入，支持一键获取临时凭证。

## 11. 典型应用场景：内部专用分组

> 场景：企业需要创建一个仅供内部员工使用的模型分组，普通用户不可见，且员工通过 LDAP 工号令牌即可自动访问。

### 11.1 场景概述

通过"分组 + 自动分组 + 渠道归属"的组合机制，可以实现对内专用模型的授权访问，同时对普通用户完全隐藏。

### 11.2 操作步骤

#### 步骤一：创建分组名称

在 **系统设置 → 模型 → 自动分组设置** 中，先确定新分组名称，例如 `internal-ai`。

#### 步骤二：配置用户可用分组（设为不可见）

在 **系统设置 → 运营 → 用户可用分组** 中，管理分组可见性。

所谓"用户不可见"，就是**不将该分组添加到用户可用分组列表**中。例如：

```json
{
  "default": "默认分组",
  "vip": "VIP 分组"
}
```

如果 `internal-ai` 不在这个列表中，普通用户在前端页面的分组选择器中将看不到它。但这**不影响**用户通过 API 使用该分组的渠道。

#### 步骤三：添加到自动分组

在 **系统设置 → 模型 → 自动分组设置** 中，将 `internal-ai` 加入自动分组列表：

```json
["default", "internal-ai"]
```

**自动分组的作用**：当令牌（Token）的分组为 `auto` 时，系统会遍历自动分组列表中的所有分组，依次尝试使用这些分组下的渠道。也就是说，`auto` 分组的令牌可以访问所有在自动分组列表中的分组所对应的渠道。

#### 步骤四：创建渠道并分配分组

在 **渠道管理** 中创建一个新渠道：

| 字段 | 值 |
|------|------|
| 名称 | 内部专用模型 |
| 渠道类型 | 根据上游选择 |
| 分组 | `internal-ai` |
| 模型 | 输入该渠道支持的模型 |
| 其他 | 正常配置 |

渠道的 `分组` 字段设为 `internal-ai`，这样该渠道只会服务于 `internal-ai` 分组的用户。

#### 步骤五：将用户分配到该分组

在 **用户管理** 中，找到目标用户（LDAP 用户），将其 `分组` 字段修改为 `internal-ai`。

### 11.3 用户访问流程

当 LDAP 用户通过工号令牌调用 API 时：

1. 用户发起 API 请求，携带 `Authorization: Bearer <工号>` 和 `LDAP-Password: <密码>`
2. LDAP 认证中间件验证身份，查找或创建用户和令牌
3. **令牌的分组**决定用户可以访问哪些渠道：
   - 如果令牌分组为 `auto` → 自动分组列表中的所有分组渠道均可访问
   - 如果令牌分组为空 → 使用用户的分组（即 `internal-ai`）
   - 如果令牌分组为 `"default"` → 只访问 `default` 分组的渠道
4. 系统在自动分组列表中找到 `internal-ai`，匹配到对应分组的渠道
5. 用户成功调用渠道上的模型

> **关于 LDAP 令牌分组**：默认创建的 LDAP 工号令牌分组为 `"default"`。要实现上述场景，需要在**自动分组设置**中包含目标分组，并且用户的令牌分组需要能匹配到这些分组。如需让 LDAP 令牌自动具备"auto"分组能力，可以在创建令牌时将 `Group` 设为 `"auto"`（系统会遍历自动分组列表中的所有分组）。

#### 前端可见性

- **模型广场**：用户可以看到自己分组（含自动分组）对应的可用模型列表
- **我的渠道**：如果渠道归属到该用户，用户可以在"我的渠道"中看到并管理
- **其他用户**：看不到 `internal-ai` 分组和对应渠道的任何信息

### 11.4 分组隔离效果总结

| 用户类型 | 能否看到分组 | 能否使用渠道 |
|---------|------------|------------|
| `internal-ai` 组成员 | API 可用（前端可见分组名） | ✅ 可以使用 |
| `default` 普通用户 | 看不到该分组 | ❌ 无法使用 |
| 超级管理员 | 完全可见 | ✅ 完整管理 |
