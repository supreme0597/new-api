# 模型响应速度排行榜 - 设计方案

> 用于团队内部交流与变更确认

---

## 一、需求概述

| 需求点 | 说明 |
|--------|------|
| 排行榜界面 | 管理员可见，简洁列表式展示 |
| 渠道来源筛选 | 支持按 A/B/所有 筛选 |
| 渠道来源映射 | 根据 base_url 自动映射到渠道来源 |
| 评分规则 | TPS×0.4 + TTFT×0.3 + 成功率×0.3，满分100 |
| 测试渠道 | 仅超级管理员可见，预留定时刷新接口 |

## 二、数据结构设计

### 2.1 渠道管理新增字段

在 `Channel` 表增加：
| 字段 | 类型 | 说明 |
|------|------|------|
| is_test_channel | tinyint | 是否为测试渠道（0=否，1=是） |
| source | varchar(64) | 渠道来源名称（如"渠道A"、"渠道B"），用于排行榜筛选 |
| sampling_interval_seconds | int | 该渠道的采样间隔（秒），`null` 时使用全局默认值 |

**说明**：
- 测试渠道的**所有模型**都会被定时采样测试
- 渠道来源由管理员手动配置，或通过 base_url 自动映射
- `sampling_interval_seconds` 用于控制该渠道每次采样时的请求间隔，避免触发限流

### 2.2 模型响应性能表 `model_performance`

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 主键 |
| channel_id | int | 关联渠道ID |
| model | varchar(128) | 模型名称 |
| tps | float | 每秒输出 Token 数 |
| ttft | int | 首次响应时间（毫秒） |
| sample_size | int | 累计采样次数 |
| updated_at | bigint | 最后一次采样时间 |

**唯一索引**: `(channel_id, model)`

### 2.3 渠道来源映射表 `channel_source_mapping`

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 主键 |
| source_name | varchar(64) | 来源名称（如 "渠道A"、"渠道B"） |
| base_url_pattern | varchar(255) | URL匹配模式（支持模糊匹配，如 `*.openai.com`） |
| priority | int | 匹配优先级（数字越小优先级越高） |

**说明**：用于自动根据 base_url 推断渠道来源，管理员也可手动覆盖

### 2.4 采样配置表 `sampling_config`

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 主键 |
| name | varchar(64) | 配置名称，如"代码测试"、"长对话" |
| prompt | text | 测试用的 Prompt 内容 |
| max_tokens | int | 期望最大输出 token 数 |
| is_active | tinyint | 是否启用（1=启用，0=禁用） |
| created_by | int | 创建者用户ID |
| updated_at | bigint | 更新时间 |

## 三、评分算法设计

### 3.1 评分公式

```
评分 = TPS分 × 0.4 + TTFT分 × 0.3 + 成功率分 × 0.3
```

### 3.2 分项计算规则

| 指标 | 计算方式 | 固定基准值 |
|------|----------|-----------|
| TPS分 | `min(TPS / 基准TPS, 1) × 100` | **100 tokens/s** |
| TTFT分 | `max(0, (1 - TTFT / 基准TTFT)) × 100` | **1000ms** |

\n
> 成功率分直接使用成功率百分比（0-100），成功率越高分数越高

### 3.3 评分标准说明（界面展示）

```
┌─────────────────────────────────────────────────────────────┐
│  📊 评分标准                                               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  综合评分 = TPS分 × 0.4 + TTFT分 × 0.3 + 成功率分 × 0.3                    │
│                                                             │
│  TPS分 = min(实际TPS / 100, 1) × 100                     │
│  ├─ 基准: 100 tokens/s                                      │
│  └─ 达到或超过基准 → 100分                                  │
│                                                             │
│  TTFT分 = max(0, (1 - 实际TTFT / 1000)) × 100            │
│  ├─ 基准: 1000ms                                            │
│  └─ TTFT越低分数越高，≥1000ms → 0分                         │
│                                                             │
│  满分: 100分                                                │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 3.4 缺省值处理

- 无 TPS 数据 → TPS分 = 0
- 无 TTFT 数据 → TTFT分 = 0
- 两者都无 → 该模型不参与排名

**排序交互**：

### 4.3 加载方式方案对比

| 方案 | 描述 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| **A. 传统分页** | 底部页码点击跳转 | 定位精准，可快速跳转任意页，知道总页数 | 需要点击，浏览中断感强 | 数据量大、需要精确跳转 |
| **B. 下拉加载更多** | 滚动到底部自动加载下一页 | 浏览流畅，无中断，适合逐条查看排名 | 无法快速跳转尾部，长时间滚动疲劳 | **推荐：排行榜场景** |
| **C. 分页+加载更多混合** | 前N页下拉加载，之后显示分页 | 兼顾流畅与定位 | 实现稍复杂 | 数据量中等 |
| **D. 虚拟滚动** | 只渲染可视区域，滚动条模拟全量 | 超大数据量不卡顿 | 实现复杂，滚动条手感差异 | 千条以上数据 |

**推荐方案：B（下拉加载更多）**

理由：
- 排行榜数据量通常不大（几十~几百条），不需要虚拟滚动
- 用户浏览排名的行为是「从上到下扫视」，滚动比翻页更符合直觉
- 排名有明确序号（1、2、3...），即使加载多页也不会迷失位置
- 模型名称本身可作为锚点，便于记忆和对比

### 4.4 设计要点

- **纯列表展示**：无表格、无卡片边框，用分隔线区分每条记录
- **加载方式**：滚动到底部自动加载下一页，加载时显示 Skeleton/Spin 占位
- **空状态**：无数据时显示提示"暂无性能数据，请先配置测试渠道并刷新采样"
- **排名展示**：
  - 前三名：🥇🥈🥉 emoji + 模型名称
  - 其他名次：数字序号（如 4、5、6...）
- **评分突出**：评分数字右对齐、大字号显示
- **信息折叠**：模型名称 + 评分在同一行，渠道/TPS/TTFT 在下一行（次要信息灰色）
- **时间显示**：更新时间用相对时间（"10分钟前"或时间戳）
- **回到顶部**：滚动超过一屏后显示浮动"回到顶部"按钮

## 六、后端逻辑设计

### 6.1 定时任务

| 任务 | 频率 | 说明 |
|------|------|------|
| 性能采样 | 每30分钟 | 对测试渠道执行请求，记录TPS和TTFT |
| 数据清理 | 每日凌晨 | 删除7天前的性能数据 |

**采样间隔控制**：
- 渠道级 `sampling_interval_seconds` 控制该渠道内模型采样的请求间隔
- 若渠道未设置，使用全局默认间隔（建议 10 秒）
- 渠道间采样顺序执行，按间隔等待，避免并发触发限流

**失败熔断**：
- 若某个渠道采样返回 429 / 401 / 403，立即跳过该渠道剩余模型
- 记录失败日志，该渠道本次采样周期不再继续

### 6.2 数据保留规则

- **保留周期**：7天
- **清理方式**：每日定时任务删除 `updated_at` 早于 7 天的记录
- **界面展示**：排行榜底部显示"最后采样时间"，各行显示相对时间（"10分钟前"、"3小时前"）

### 6.3 渠道来源匹配逻辑

```go
// 伪代码
func MatchChannelSource(channel *model.Channel) string {
    // 1. 先匹配 base_url_pattern（精确/模糊）
    // 2. 再按 channel_type 匹配
    // 3. 都无匹配 → 返回 "默认"
}
```

### 6.3 TPS/TTFT 采样方式

1. 向测试渠道的指定模型发送固定 prompt
2. 流式响应，计算输出 token 数 / 耗时 = TPS
3. 从请求到收到第一个字节的时间 = TTFT

### 10.2 采样执行逻辑

1. 管理员启用 1 个或多个采样配置
2. 定时任务遍历所有**测试渠道**
3. 对测试渠道下的**每个模型**发送 prompt
4. 记录 TTFT 和实际输出的 TPS
5. 同一模型可能有多条采样记录（来自不同配置）

### 10.3 采样频率配置

新增**系统配置表**或扩展现有系统配置：

| 字段 | 类型 | 说明 | 默认值 |
|------|------|------|--------|
| sampling_interval | int | 采样任务执行周期（分钟） | 30 |
| default_sampling_interval_seconds | int | 默认渠道采样间隔（秒） | 10 |

**说明**：
- **采样任务周期**：多久执行一次完整的采样任务，建议 15~120 分钟
- **渠道采样间隔**：同一渠道内各个模型采样请求之间的时间间隔，建议 5~30 秒
- 渠道可单独设置 `sampling_interval_seconds` 覆盖全局默认值
- 间隔过短会增加系统负载和 API 调用成本
